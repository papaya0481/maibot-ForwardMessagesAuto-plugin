# 自主跨群转发功能设计

## 1. 文档状态

- 当前阶段：首版代码已实现，等待 SnowLuma/QQ 实际群聊联调
- 适用范围：MaiBot 第三方插件，仅在 SnowLuma Adapter 下的 QQ 群聊中开发验证，不修改 MaiBot 主程序
- 当前实现：查看资格跟随当前 Planner 上下文，不设置完整内容缓存 TTL；
  已完成 target 使用不按时间过期的持久化防重状态

## 2. 功能目标

本插件让 MaiBot 在一个群聊中看到值得分享的合并转发消息时，先由源群 Planner 理解完整内容并决定是否分享，再由插件按照明确配置把消息转发到一个或多个目标群。每次转发成功后，目标群自己的 Planner 会结合该群近期上下文，自主决定是否补充一句整体看法。

功能应保持以下分工：

- 源群 Planner 负责理解消息并决定“是否值得转发”。
- 插件负责权限校验、白名单路由、消息重建、顺序投递、上下文注入和任务状态。
- 目标群 Planner 负责结合目标群关系、记忆和聊天窗口决定“是否发表看法以及如何表达”。

初版不让 LLM 选择目标群。目标群完全由配置白名单决定，以避免在尚无稳定群聊画像时产生不可预测的跨群分享。

## 3. 名词与边界

### 3.1 Source

Source 是读取当前消息并触发一次分享任务的群聊。只有列入 source 白名单的群才能调用转发工具并创建任务。这里的 source 不表示合并转发节点最初产生或首次发送的群；其他群的内容被转入 source 群后，只要该消息现在属于 source 聊天流，仍可由 source 群 Planner 决定继续分享。

每个转发任务只对应：

- 一个 source 聊天流；
- 一条 source 合并转发消息；
- 一个明确的 source `msg_id`。

### 3.2 Target

Target 是接收合并转发消息的目标群聊。只有列入 target 白名单且能够解析到有效聊天流的群才允许接收消息。

一个任务可以包含多个 target。插件按照配置中的既定顺序逐个处理，不并行发送。

### 3.3 白名单

初版只提供两个独立白名单：

- source 白名单：允许读取当前聊天流内的消息并发起分享任务的 QQ 群号；
- target 白名单：允许接收插件转发消息的 QQ 群号。

不提供黑名单，也不采用“除黑名单外全部允许”的隐式规则。新增群聊不会直接获得 source 或 target 权限。

初版固定使用 SnowLuma Adapter 和 QQ 平台，因此配置中只保存群号，不增加 `platform`、`account_id` 或其他复合路由字段。插件运行时负责根据群号解析对应聊天流。

## 4. 完整处理流程

### 4.1 源群查看与决策

1. source 白名单中的群收到一条合并转发消息。
2. MaiBot Planner 根据消息预览决定调用 `view_forward_message(msg_id)`。
3. `view_forward_message` 展开合并转发的完整内容，包括必要的图片或复杂消息分析结果。
4. Planner 根据完整内容、源群语境和聊天关系决定是否分享。
5. 如果决定分享，Planner 调用插件提供的 `@Tool`，例如：

   ```text
   request_cross_group_forward(
       msg_id="源消息 ID",
       sharing_reason="简短说明为什么值得分享",
       content_summary="连续可重试故障或连续空内容时使用的忠实摘要"
   )
   ```

`msg_id` 为必填参数。`sharing_reason` 可以作为日志和目标群提示；
`content_summary` 只在连续可重试故障达到阈值或连续两次返回空内容时作为
降级信息。成功查看结果只要仍在当前 Planner 上下文中，就必须使用完整内容，
不得因为经过一段时间而降级。工具描述必须明确要求 Planner 仅在成功查看
合并转发完整内容并确实认为值得分享时调用。

### 4.2 插件接收请求

插件工具被调用后必须依次验证：

1. 调用来自群聊环境；
2. 当前聊天流属于 source 白名单；
3. `msg_id` 属于当前 source 聊天流，不能通过猜测 ID 读取其他聊天流中的消息；不限制合并转发节点最初来自哪个群；
4. 目标消息确实包含合并转发节点；
5. 当前 Planner 上下文仍包含该 `msg_id` 的成功
   `view_forward_message` 调用及完整结果，或已经满足明确的失败降级条件；
6. 当前 target 中尚未完成的群可以继续处理；相同 source、`msg_id` 和
   target 已经转发过时返回幂等结果，不再次发送；
7. 至少存在一个可用的 target 白名单聊天流。

工具不应在一次 Planner RPC 内完成所有目标群投递。验证通过后应创建后台任务并快速返回任务 ID，以避免多个目标群、媒体读取或网络发送导致 Tool 超时。

首版实现的 Tool 名称为 `request_cross_group_forward`。它位于 MaiBot 的 deferred tools 池中，Planner 先看到名称和简要说明，需要时通过 `tool_search` 发现完整参数并在后续轮次调用。Tool discovery 不承担授权职责；处理器必须实时执行完整的 QQ 平台、source 群白名单、当前聊天流和消息归属校验。

### 4.3 顺序投递

后台任务按照 target 白名单中的配置顺序逐个执行：

1. 解析 target 的精确聊天流；
2. 使用源消息保存的原始转发节点调用 `ctx.send.forward`；
3. 只有实际发送成功后，才向目标群 Maisaka 上下文追加消息；
4. 上下文写入成功后，调用 `ctx.maisaka.proactive.trigger` 强制触发一轮目标群 Planner；
5. 记录该 target 的发送、上下文写入和 Planner 入队结果；
6. 继续处理下一个 target。

初版“顺序处理”的含义是发送动作和主动任务入队按 target 顺序发生。当前 SDK 的主动任务接口只确认任务已经入队，没有等待 Planner 完成或取得最终回复状态的接口。因此，不保证目标 A 的 Planner 已经推理或回复完成后，目标 B 才开始推理。

如果未来必须严格等待上一目标群 Planner 完成，需要 MaiBot 主程序提供主动任务完成回调或状态查询能力。在获得明确许可前，本插件不得为此修改 MaiBot 主程序。

## 5. 消息内容与查看资格

### 5.1 两类内容

插件需要区分两类数据：

- 原始转发节点：保留发送者、消息节点、文字和媒体消息段，用于重建并实际发送合并转发。
- 已展开完整内容：`view_forward_message` 返回的可读文本和媒体分析结果，用于目标群 Planner 理解内容并决定是否发表看法。

原始节点可以通过 `msg_id` 和 source 聊天流从 MaiBot 消息能力中重新读取。读取媒体消息时应请求必要的二进制数据。

### 5.2 上下文内查看资格

Planner 的前一个工具结果不会直接成为后续插件 Tool 的参数。为复用 `view_forward_message` 的完整结果，推荐使用阻塞式 `maisaka.planner.before_request` Hook：

1. 仅检查 source 白名单聊天流的 Planner 请求；
2. 从 Planner 历史中识别 `view_forward_message` 的 tool call；
3. 根据 `tool_call_id` 找到相应 ToolResult；
4. 提取 `msg_id` 和完整展开内容；
5. 将当前请求中仍可见的成功结果登记为
   `(source_stream_id, msg_id)` 的查看资格，并供转发 Tool 读取完整内容。

阻塞模式用于保证紧接着的 Planner 内部续轮开始前查看结果已经可用。成功
结果只要仍存在于当前 Planner 上下文，就持续有效，不设置缓存时间、过期
时间或滑动 TTL，也不因等待新消息、Planner 请求重试或经过较长时间而降级。
如果上下文裁剪已经移除对应调用或 ToolResult，该消息不再具备查看资格；
Planner 必须重新调用 `view_forward_message`，不能用“曾经查看过但已过期”
作为摘要降级理由。

实现可以维护仅用于解析加速的进程内索引，但该索引不得延长查看资格。每次
Hook 都必须以当前 Planner 上下文为准，同步移除已经不可见的结果。资格记录
至少包含：

- source stream ID；
- source `msg_id`；
- `tool_call_id`；
- 完整展开文本；
- 可选的内容摘要或哈希；
- 当前上下文中是否仍可见。

当前 Host 的 `maisaka.planner.before_request` 消息载荷不包含 ToolResult
`success` 字段。插件暂时根据当前内置工具和统一工具注册表的稳定失败前缀
区分成功与失败；已知失败文本不得登记为完整内容或查看资格。未来应由 Host 提供
结构化执行状态，详见 [TODO](TODO.md)。

插件按失败语义维护状态：

- 展开异常、工具调用或注册能力暂时不可用属于可重试故障，只连续累计同类
  故障；达到 `behavior.view_failure_fallback_threshold` 后允许降级，默认
  值为 `2`，最小值为 `1`；
- 空内容使用独立计数，首次要求再进行一次诊断查看，连续第二次仍为空时
  允许降级；
- 参数无效或消息不存在属于可修正错误，必须修正 `msg_id`，重复相同错误
  不累计；
- 目标不是可展开的合并转发属于终止错误，立即拒绝且永不通过重试开放降级；
- 无法安全分类的失败保守拒绝，不自动累计。

当前上下文没有成功查看记录、可重试故障未达到阈值或首次空内容时，不允许
直接降级。成功查看记录一旦存在且仍在上下文中，应始终使用完整内容。只有
满足以下任一失败条件时，才允许依次使用 `content_summary`、原消息预览和
固定占位文本：

- 同一 source stream 与 `msg_id` 的连续可重试故障达到配置阈值；
- 同一 source stream 与 `msg_id` 连续两次返回空内容；

降级不阻止原始合并转发节点发送，但必须在任务日志中说明原因和实际采用的
上下文来源。

### 5.3 已转发状态与防重

查看资格和重复转发校验是两个独立问题：

- 查看资格只证明 Planner 已在当前上下文理解该消息，不持久化过期时间；
- 已转发状态用于证明相同 source、`msg_id` 和 target 已经创建或完成过任务，
  必须持久化，不能因为 Planner 上下文变化而丢失；
- 转发 Tool 在确认查看资格后检查幂等状态；如果消息已经转发过，返回已有
  任务信息，不重新发送到任何已完成 target；
- 已完成 target 的防重记录不设置时间过期；配置新增 target 时只处理尚未
  完成的新 target，不得为了更新路由而重发旧 target；
- 防重记录不得被当作完整内容来源，也不得触发摘要降级。

### 5.4 目标群上下文

不能只依赖发送能力隐式同步 Maisaka 历史，因为目标群运行时可能尚未创建。每个 target 发送成功后，插件应显式调用：

```text
ctx.maisaka.context.append(
    target_stream_id,
    segments=[合并转发消息段],
    visible_text=源群已展开的完整内容或降级摘要,
    source_kind="cross_group_forward:<job_id>",
    message_id="<job_id>:<target_stream_id>"
)
```

这一步确保目标群运行时存在，并让目标群 Planner 获得无需再次调用 `view_forward_message` 的可读内容。

## 6. 目标群看法

上下文写入成功后，插件应通过 `ctx.maisaka.proactive.trigger` 发起主动任务。意图应表达：

- 麦麦刚刚把一则来自其他群的合并转发分享到了本群；
- 完整内容已经位于当前上下文，不需要再次调用 `view_forward_message`；
- 应结合本群近期聊天、群友关系、记忆和表达习惯判断是否回应；
- 有自然且有价值的看法时，可以回复一句；
- 没有合适内容时应保持沉默；
- 不要机械复述整则转发，也不要暴露插件内部流程。

初版优先使用目标群 Maisaka Planner，而不是由插件内部单独调用 LLM 生成看法。这样能够复用目标群自己的关系、记忆、人格表达和正常回复工具链。

## 7. 路由配置

预期配置结构至少包含：

```toml
[plugin]
version = ""
config_version = ""

[routing]
source_groups = ["123456789", "234567890"]
target_groups = ["345678901", "456789012"]

[behavior]
view_failure_fallback_threshold = 2
trigger_target_planner = true
```

群号使用字符串保存，避免配置解析或数值类型差异。`target_groups` 的排列顺序就是转发处理顺序。具体字段声明可以在实现阶段根据 maibot-plugin-sdk 的配置模型调整，但必须保持：

- source 与 target 白名单分离；
- 白名单成员只使用 QQ 群号；
- 仅支持 SnowLuma Adapter 下的 QQ 群聊；
- target 顺序与配置列表顺序一致；
- 未明确列出的群没有权限；
- 插件版本和配置版本同步；
- 配置更新后重新校验群号、聊天流和重复 target。

## 8. 失败处理

每个 target 应独立记录状态，单个目标失败不应让已经成功的目标回滚，也不应默认阻止后续目标继续处理。

推荐状态包括：

- `pending`
- `sent`
- `context_appended`
- `planner_queued`

首版只持久化已经成功到达的阶段。失败和跳过原因写入日志，不把临时失败固化成终态，以便后续再次请求时从最后一个成功阶段继续。

处理原则：

- 物理发送失败：不注入上下文，不触发 Planner，记录失败后继续下一 target。
- 发送成功但上下文注入失败：保留已发送消息，记录降级，不触发缺少上下文的 Planner。
- 上下文成功但主动任务入队失败：保留消息与上下文，记录失败，不重复发送消息。
- 插件重载或重启：从插件数据目录中的 `forward_state.json` 恢复阶段记录，避免同一 source 消息被重复转发。
- source 或 target 配置在任务执行前失效：跳过该目标并记录原因。

## 9. 安全与行为约束

- 工具处理器必须再次校验 source 白名单，不能只依赖 Planner 是否展示工具。
- Planner 不得通过工具参数自行指定任意 target；目标集合只能来自插件配置。
- 使用 source stream ID 和 `msg_id` 联合查询消息，防止跨会话读取。
- 按 source stream、`msg_id` 和 target 建立永久防重键；已经完成的 target
  不因时间经过、上下文裁剪、插件重载或路由调整而重新发送。
- 配置转发冷却时间和单位时间最大任务数，防止异常扩散。
- 记录必要的任务元数据，但日志中不重复输出大量私聊内容、完整媒体 Base64 或敏感标识。
- 适配器通常会忽略机器人自己的入站回声，但插件仍必须使用幂等和来源标记防止循环转发。
- 用户可见的错误、状态和配置说明优先使用简体中文。

## 10. 已知限制

- 当前不能等待某个目标群 Planner 完整结束后再触发下一个目标群。
- 转发属于读取节点后重新组装，未必与 QQ 原始合并转发对象完全一致。
- 文字、图片、表情和常规语音应优先支持；嵌套转发、文件及特殊 OneBot 消息段需要单独验证并提供降级行为。
- `view_forward_message` 查看资格依赖 Planner Hook 的消息序列化结构和当前
  上下文裁剪边界，需要覆盖兼容性测试。
- 目标群仍需消耗一次 Planner 推理来结合自己的上下文理解内容；复用源群
  当前上下文中的展开结果只能避免重复展开和媒体分析，不能消除目标群推理。

## 11. 测试要求

实现后至少应覆盖以下测试。

### 11.1 单元测试

- source 白名单允许和拒绝逻辑；
- target 白名单解析、去重和顺序保持；
- 非合并转发消息拒绝；
- `msg_id` 不属于 source stream 时拒绝；
- 当前上下文中的 `view_forward_message` ToolResult 提取与查看资格；
- 成功查看结果仍在上下文时始终使用完整内容，不因时间经过而降级；
- 查看结果被上下文裁剪后要求重新查看，不允许按“过期”摘要降级；
- 当前上下文没有成功查看记录和可重试故障次数未达到配置阈值时拒绝降级；
- 可重试故障达到配置阈值或连续两次空内容时允许摘要降级；
- 可修正、终止和未知失败不会因重复调用获得降级资格；
- 自定义 `view_failure_fallback_threshold` 只改变可重试故障的降级次数；
- 成功查看后续轮提醒在 Planner 被新消息打断时不会丢失；
- 原始转发节点到 `ctx.send.forward` 参数转换；
- 同一消息重复调用时的幂等处理；
- 发送失败后不注入上下文；
- 上下文失败后不触发 Planner；
- 多 target 始终按配置顺序调用发送和主动任务接口；
- 配置版本与插件版本一致性。

### 11.2 集成测试

- SnowLuma 下文字合并转发的跨群发送；
- 包含图片、表情、语音的合并转发；
- 一个 source 对多个 target 的顺序投递；
- 目标群 runtime 不存在时仍能先创建上下文并触发 Planner；
- 目标群 Planner 能读取完整展开内容且无需再次调用 `view_forward_message`；
- 目标群 Planner 选择回复和选择沉默的两种路径；
- 单个 target 发送失败时后续 target 仍继续执行；
- 插件重载后不会重复转发已经处理的任务。

### 11.3 人工验收

使用至少三个测试群：一个 source、两个 target。发送一则包含多节点和图片的合并转发，确认：

1. source Planner 先查看完整内容；
2. 只有 Planner 判断值得分享时才调用插件工具；
3. 两个 target 按配置顺序收到合并转发；
4. 每个目标群获得自己的上下文并分别决定是否评论；
5. 同一 source 消息不会被再次转发；
6. 非白名单群无法触发或接收消息。
